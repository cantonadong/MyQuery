# MyQuery 与 MyBI 共享查询核心长期方案

记录日期：2026-11-10

本文记录长期架构结论，不代表下述改造已经完成。

## 结论

独立维护一份 Rust 查询核心源码，同时提供 Rust 库和 C ABI 共享库接口。MyQuery 直接引用 Rust 库；MyBI 的后台查询进程加载 Windows DLL 或 Linux `.so`。

保留 DLL／共享库方式。DLL 是交付形式，“只维护一套代码”由共享核心源码保证，不要求所有调用方都经过 DLL。

```text
独立 Rust 查询核心（一份源码、统一版本）
├─ Rust 库 → MyQuery EXE
├─ Windows DLL → MyBI Windows 后台查询进程
└─ Linux .so → MyBI Linux 后台查询进程
```

## 职责边界

| 模块 | 职责 |
| --- | --- |
| 共享查询核心 | PostgreSQL／Redshift 连接、TLS、SQL 执行、取消、超时、结果限制与读取、数据库元数据、数据库错误处理 |
| DLL／共享库接口 | 请求与结果适配、资源生命周期和接口兼容检查；复用核心，不另写查询实现 |
| MyQuery | 编辑器、窗口交互、本地配置和密码存储 |
| MyBI | 报表、权限、数据源凭据管理、定时任务、数据集转换、缓存和快照发布 |

核心提供执行机制，各应用决定使用策略。例如 MyBI 使用只读、单结果集限制，MyQuery 保留交互查询和多结果集能力。

## 当前基础

- MyQuery 的 `src/main.rs` 已引用 `myquery_core`，核心由 `src/lib.rs` 导出。
- `Cargo.toml` 同时生成 `rlib` 与 `cdylib`；EXE 和 DLL 使用同一份核心源码。
- MyBI 后端通过 `query_core.py` 调用 DLL，远程查询、连接检查和元数据读取已接入。
- 当前 EXE 和 DLL 各自包含核心机器码，属于产物重复，不等于维护两份实现。修复核心后仍需分别构建、更新调用方产物。

## 后续演进

1. 将查询核心整理成独立项目或包，解除 Slint、窗口和 Windows 密码存储等应用依赖；数据库相关重复逻辑逐步归入核心。
2. 统一核心版本和构建发布，MyQuery 固定依赖版本，MyBI 固定共享库版本，并检查 ABI 兼容性。
3. 支持服务器平台：同一份源码构建 Windows DLL 和 Linux `.so`，MyBI 按平台加载。
4. 按实际负载补齐有上限的连接复用、查询取消和分批结果读取。保留共享库方式，不要求保留当前每次新建连接、临时 JSONL 文件交接的接口形态。
5. MyBI 服务器由后台任务进程加载共享库，刷新并发布数据快照；API 和浏览器读取已发布结果。调度、重试和快照发布不进入查询核心。

连接复用与分批读取属于性能演进方向，具体收益需要实测。单纯的同进程 DLL 调用通常不是主要开销，连接建立、TLS 握手、序列化和大结果中转更值得关注。

## 其他方案与适用条件

- 不强制 MyQuery 改走 DLL：直接 Rust 调用可以复用同一源码，保留完整交互能力，避免额外接口转换和部署依赖。
- 当前不建立独立网络查询服务：MyBI 有服务器，不代表查询核心必须单独成为网络服务；后台进程直接加载共享库即可。
- 将来若明确需要多个应用跨机器共用查询节点、统一保管数据库凭据或集中限制数据库负载，再在同一核心外增加服务层，继续复用核心实现。

## 风险与约束

- 应用与共享库版本不匹配是主要维护风险，需要可追踪的版本发布和接口兼容检查。
- 当前 DLL 的只读、单结果集接口不能直接替代 MyQuery 的持久会话、进度回报、取消和多结果集需求。
- 服务器凭据和密钥需由服务器管理，不能依赖桌面机器的 Windows 用户环境。
- 本文为源码检查后的架构结论，未进行服务器部署验证或性能基准测试。
